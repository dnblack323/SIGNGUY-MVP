## EC16 execution, privacy and reconciliation

`ProviderExecution` is an optional server-only adapter argument to the existing Gateway request function, not a client flag or a second lifecycle. The original reservation/commit/release helpers and configurable capability charge are unchanged. Credit confirmation is checked against the current server capability. Deterministic composition never enters the Gateway. Client-supplied usage/cost/simulation cannot authorize paid execution.

Request identity binds tenant, staff user, product/store, saved revision, variant/color/size and model. Same-key replays return the original action, including after interruption; changed inputs or generic-endpoint replay of a private adapter request are rejected. A Mongo atomic lock on the canonical credit account serializes Gateway admission/settlement; a bounded admission wait does not retry HTTP. Outstanding reserved charges and unknown provider-cost estimates count toward existing daily limits. Unresolved same-product requests are checked again inside this admission boundary, preventing new-key races. Requests remain rate-limited by the existing policies. The initial implementation conservatively permits one executing Gateway action per tenant; it adds no queue or alternate balance.

Before dispatch, a cost estimate and stable client request ID exist. Transport has no retries or redirects, a 10-second connection timeout, 180-second per-read timeout and a 190-second overall deadline. Explicit provider rejections release reserved customer credits; invalid decoded output releases the customer charge while retaining estimated provider expense. Timeouts, 408/409, 5xx, missing/inconsistent usage, interrupted storage or settlement retain the executing action/reservation and require reconciliation. They never automatically regenerate. The UI offers a read-only status refresh and blocks another unresolved product request. Delivered images rejected for appearance retain the existing successful-generation charge; no new refund policy or refund engine is introduced.

Provider token breakdowns and the approved rate snapshot calculate an **estimated expense**, rounded up to integer USD micros; `actual_cost_micros=null`, status `estimated`, until invoice reconciliation. Unknown cost is not recorded as a confirmed zero. The admission estimate is not an upstream hard dollar cap: the image API has no request-level dollar ceiling, and GPT Image 2.5 token consumption has not been measured. Live testing therefore also needs a controlled provider project/account budget and measured usage before subsequent requests.

For an interrupted request, operations must inspect the canonical action's private `_provider` receipt, client request ID, provider response ID when available, usage, file reference/hash and the existing credit/usage/provider-cost ledgers. Do not clear a lock, change an idempotency key, redispatch, or replay settlement blindly. Confirm provider receipt/expense, asset persistence and any completed credit ledger transition first; use the existing EC16 reconciliation/adjustment procedures under the appropriate authorization. A crashed lock has no automatic expiry. There is no new automatic reconciliation UI or claim of crash-atomic ledger transactions; uncertain cases deliberately fail closed for manual reconciliation. Generic history/replays project canonical public action fields and exclude private receipt/input bindings; product-scoped staff endpoints enforce current access to images/status/review.

OpenAI standard output sizes include 1024 square, 1536x1024 and 1024x1536; flexible dimensions have divisibility/aspect/pixel limits and larger experimental sizes. This increment intentionally accepts only 1024 square and generation, even though editing/image input are documented. No logo-redrawing guarantee is inferred. Published OpenAI tiers list Free unsupported, Build 20 images/min and 250k tokens/min, Launch 150/3M, Grow 250/8M. Project access, billing, verification and actual limits are unverified; organization verification may be required. BFL documents up to 24 concurrent requests for most endpoints, request-ID polling, and ten-minute delivery expiry; numeric account-specific limits/usage invoice access still require verification. A timed-out POST cannot safely be treated as a free failure for either provider.
