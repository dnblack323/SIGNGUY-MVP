## Implemented behavior

In the existing Images and Mockups section, a compact disclosure adds flat-front T-shirt/hoodie composition. Staff selects authorized PNG/JPEG/WebP files and an active, manually available colored variant; transparent PNG artwork is recommended. Four percentage controls define a bounded decoration area. The backend centers an aspect-preserving copy of the actual artwork in that area, preserving alpha and avoiding model redrawing, stretching or cropping. Original file bytes remain unchanged. A starting area is offered for adjustment, never represented as a verified physical print size or manufacturing capability.

Preview returns an authenticated, no-store PNG without persisting a file. Its digest binds pixels, source hashes, placement, variant, product revision and staff identity. Acceptance requires explicit staff review, a description and that exact digest; the backend rerenders and checks current inputs/revision. Changed settings/sources require a new preview. A late frontend preview cannot authorize different current settings. Validation errors remain readable for blob responses.

Acceptance writes a new canonical internal FileRecord/FileLink and existing reviewed WebstoreMockup (`generation_source=deterministic_composition`), preserving source hashes/placement/product/variant provenance in its `preparation` field. It reuses/creates the canonical artwork reference, adds selections to the private editor draft, and requires existing Save Product before explicit submission. It never automatically submits, approves or publishes. New private revisions get new file/mockup identities; old submitted identities are not replaced.

The server validates Webstore write/read access, explicit assignment scope, tenant/store/product/file membership, product revision/status, variant/color/status/manual availability, finite bounded coordinates, decoded single-frame format, byte/dimension/pixel limits. Sources are private managed files, not arbitrary remote URLs. Rendering runs off the async event loop. New PNG output strips source EXIF/text metadata. Composition accepts at most 12 MB per input, 16 megapixels and 6000 pixels per edge (minimum 16). Unsupported vectors/PDF, animated images, hats/curved views, perspective/fabric deformation and color proofing use the existing manual prepared-upload fallback. SVG security is unchanged; compatible SVG preview remains separate work.

This is deterministic image preparation, with no AI execution, capability charge or provider expense. Configured AI credit prices/allowances remain untouched. The existing AI panel and Gateway continue to identify local demonstrations and refuse unconnected paid generation.

## Provider assessment (documentation research only)

**Provisional initial choice: OpenAI GPT Image 2**, with a version pinned for evaluation (`gpt-image-2-2026-04-21`). This recommendation is an integration judgment based on documented image input/edit support and the Assistant branch's existing OpenAI direction, not measured superiority. The [official model page](https://developers.openai.com/api/docs/models/gpt-image-2) documents generation/edit endpoints and image input/output. Account access/rate limits still need verification under separately authorized evaluation. Newer Image2.5 models exist; they were not silently selected or enabled.

The [official image guide](https://developers.openai.com/api/docs/guides/image-generation) lists PNG/JPEG/WebP output and warns about text/brand consistency and precise composition limitations. Its GPT Image2 table estimates **1024-square output only** at **$0.006 low / $0.053 medium / $0.211 high**, with text/reference-image inputs charged additionally. These are provider estimates, not customer prices or a per-request total. Use explicit size/quality and observed usage/cost; do not infer a fixed credit conversion. Fetch request IDs and distinguish known refusal/rate-limit failure from ambiguous timeouts. No availability, latency, apparel consistency or quality was measured here.

**Reasonable alternative: BFL FLUX.2 [pro]**. Its [editing documentation](https://docs.bfl.ai/flux_2/flux2_image_editing) describes multi-image reference editing and up to4MP output. [BFL's price table](https://help.bfl.ai/articles/7986977817-what-are-the-costs-associated-with-using-your-models) lists generation from **$0.03/MP**, editing from **$0.045/MP**, with resolution rounding. These are starting quotes, not measured invoices or customer-credit rates. [Execution documentation](https://docs.bfl.ai/quick_start/generating_images) returns request ID/polling URL with Ready/Failed/Error states; persist the original job and poll it rather than resubmitting uncertain work. Confirm endpoint-specific image formats/usage billing before an adapter. [BFL's licensing guidance](https://help.bfl.ai/articles/9272590838-self-serve-dev-license-overview-pricing) says hosted API usage includes commercial rights; self-hosted weights have different licenses. No BFL implementation/account was added.

Neither provider establishes exact garment/color/decoration fidelity. A matching photographed blank plus deterministic original artwork is more reliable for identity preservation than asking a model to recreate branding. This is a design inference, supported by the repeatable composition tests, not an AI image benchmark. Future AI should generate an unbranded presentation/background kept separate from canonical product and logo data, then use original artwork locally. Staff must reject changed garment details or color. A better-looking image is not manufacturing proof. Review provider business/data/usage terms and rights to the input photos/customer artwork before transmission; no terms accepted/account provisioned in this increment.
