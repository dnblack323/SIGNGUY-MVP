## 4. Proposed turn, privacy and cost contracts

1. **Authenticate and authorize first.** Existing staff assistant permission, release/entitlement checks and commercial restrictions still apply. Resolve `(tenant_id, user_id)` on the server. Private conversation access has no automatic owner/admin bypass; later explicit sharing is outside B. Deny foreign IDs without revealing their contents/existence.
2. **Claim one turn.** Require a stable request key for the real conversational path. An atomic tenant/user/conversation-scoped claim prevents duplicate messages, calls or charges. Serialize or reject overlapping turns in one conversation, and compare payload identity on retries. A retry resumes/returns the existing outcome; it does not blindly repeat a possibly paid call.
3. **Build bounded permitted context.** Load canonical user/assistant/tool items, necessary provider continuation items, a bounded conversation summary and approved user memory. Recheck source permissions before reusing stored tool data; permission loss must not replay forbidden records from old messages/summaries. Strip untrusted roles/instructions. Current records supersede saved business facts.
4. **Call a server-controlled provider adapter.** Use Responses with schema-constrained functions and validate arguments again in MVP; the application executes reads, not the model. This follows [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling). Prefer application-managed bounded history with `store: false`, as supported by [OpenAI conversation-state guidance](https://developers.openai.com/api/docs/guides/conversation-state); that setting is not a promise of zero provider retention. MVP remains the history authority. Reapply current safety/personality instructions on every turn/continuation; do not depend on an external response ID as authorization.
5. **Admit actual cost before dispatch.** Reuse Gateway credit reservation and daily governance; atomically include in-flight provider spend. Bound model calls, output, tool rounds, context and timeout with server policy. Missing model/rate/budget configuration fails closed for paid dispatch; do not invent zero rates or fallback credits. Keep admission/reservation state on existing canonical Gateway records; no second wallet. No client control of credentials, model allowlists, rates, ledger amounts or simulated success.
6. **Run read tools and answer from evidence.** Return typed bounded data, citations and explicit unavailable/partial states. Clarify ambiguous targets. Render financial amounts, dates and links from validated results; unsupported model references are not accepted as citations. A natural-language action request may prepare a visible proposal using current safety contracts, but B introduces no auto-confirm/execute tool. E remains the launch action-completion gate.
7. **Finalize observed usage honestly.** Keep one parent turn and identifiable provider attempts/tool continuations; record input/output usage and provider event IDs without double charging on retries. Separate provider cost from customer credits. Estimates are marked estimated; unknown or interrupted usage is incomplete, not “actual zero.” Existing numeric cost fields require additive provenance/status handling so placeholder numeric fields never masquerade as measured cost. Provider usage may be chargeable even if an answer fails; reconcile uncertainty and stop further unreserved work. Do not silently refund actual provider liability away.
8. **Persist and present the outcome.** Save messages, cited result references, user-approved context and request status on existing records; record sanitized audit/usage metadata. Return retryable error or partial result honestly if later persistence/finalization fails. Never claim model-backed success from the deterministic fallback. Secrets/private prompts stay out of browser responses and logs.

Read-only tools may create assistant-owned message/context/citation/usage evidence, but must not mutate Customers, Orders, Invoices, Payments, schedules or production. No paid request is needed for settings saves, history, direct navigation, user-approved memory save or a deterministic quick action. Avoid classifier/parser/rewriter chains and periodic background prompts. Summarize only at a bounded history threshold through the same metered capability; full memory retention/correction workflow completion stays in E.

## 5. Employee workflow and personality/settings boundary

The employee opens the dock or full page, selects/resumes their private conversation and asks “Which invoices are overdue?” The response identifies its criteria and links relevant permitted records. “Which is oldest?” retains those references and refreshes balances when needed. From a Customer page, “Summarize their recent Orders” validates the page reference and access. Production/schedule answers distinguish recorded facts from unavailable causes. No customer or buyer receives a message or document from these reads.

Both interfaces use one current-user state owner. Use server history as authoritative; keep an active conversation reference scoped to tenant/user, never an unscoped browser transcript. Clear state and abort/discard old requests on logout, identity change or access loss. Opening both surfaces, React remounts or retrying must not send duplicate prompts. A reopened conversation retains context without copying another user's state.

Basic Assistant Settings includes all five approved identities: Sharp Ops Partner, Wise Mentor, Cheerful Helper, No-BS Direct and Sarcastic & Funny, with the exact warning/description/rules in the [integrated plan](BUSINESS_ASSISTANT_V1_IMPLEMENTATION_PLAN.md#2-five-personality-cards-and-shared-definition). GET/PUT `/api/assistant/preferences` is a proposed addition, not an existing endpoint. Use `ops_partner` when unset; shop-default UI is unnecessary for B.

Changing personality affects the next turn without deleting conversations or memory. Voice remains an independent preference; B must not label a voice compatible, previewable or working before C/D. All personalities share facts, tools, permissions and confirmation rules. Sensitive topics use caring professional language. Customer-facing draft generation excludes personal tone and uses the professional output policy; no automatic email sending. Response-length/display-name settings may share the typed preference boundary; UI polish remains secondary.

### Usage, money and failure behavior

Each text turn reserves canonical credits and a conservative provider-cost bound before dispatch. Tenant admission serializes simultaneous text turns across processes; in-flight cost/credits count toward configured governance. Stable user-scoped request keys and per-conversation claims prevent duplicate dispatch/accounting. Different payloads cannot reuse a request key. Missing allowed model, credential, sourced rates, budget or credits blocks paid dispatch. Nothing activates automatically.

Observed provider token usage and event IDs are recorded on canonical action/usage records. Monetary cost remains an **estimate**, using a saved rate/source snapshot; `actual_cost_micros` stays **null** because a token response is not verified monetary billing evidence. Failed turns release customer credits while preserving provider-cost liability. Fully observed failed tool loops retain known usage; timeouts/missing usage retain an explicitly incomplete conservative reserve. Pre-dispatch failures record no provider request and a zero estimate. Finalization interruption never redispatches or silently clears reserved credits. Platform totals distinguish unverified estimates from recorded actual costs and count dispatch attempts.
