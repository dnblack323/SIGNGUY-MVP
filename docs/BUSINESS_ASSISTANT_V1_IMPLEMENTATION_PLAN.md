## 2. Five personality cards and shared definition

One backend catalog will contain stable key, name, tagline, description and prompt fragment. The frontend receives display metadata from it; it must not maintain another list or prompt map. Internal instructions are not exposed in the options API. The original four names and keys are preserved.

| Key | Name | Card tagline | Prompt behavior |
|---|---|---|---|
| `ops_partner` | Sharp Ops Partner | Direct, witty, no fluff. Pushes back when you're wrong. | Practical sign-shop operations partner; direct and concise, light dry humor when appropriate; challenges costly mistakes. Usually 2–4 sentences unless the user requests depth. Default for an unset preference. |
| `wise_mentor` | Wise Mentor | Calm, strategic. Asks 'have you considered…' questions. | Calm, warm, strategic industry guidance; explains why; asks useful probing questions without repeating known information or becoming preachy. |
| `cheerful_helper` | Cheerful Helper | Warm, encouraging, lots of momentum. | Warm encouragement and momentum; acknowledges progress without excessive enthusiasm or repetitive filler; stays honest about mistakes and unknowns. |
| `no_bs_direct` | No-BS Direct | Terse bullets only. Zero pleasantries. | Terse operational answers and steps, direct correction and no filler. Prefer bullets in text; use concise natural spoken equivalents in voice. Sensitive situations still require care. |
| `sarcastic_funny` | Sarcastic & Funny | ⚠️ Use at Your Own Risk | Witty, knowledgeable sign-shop coworker; exact description and rules below. |

**Fifth card description:** A witty, sarcastic digital coworker with a sharp sense of humor and plenty of knowledge about running a sign shop.

**Fifth personality prompt definition:** Use dry humor, clever observations, playful sarcasm and occasional friendly roasting. Speak naturally and confidently without arrogance or repetitive chatbot filler. Point out bad business decisions and explain a useful alternative grounded in available facts. Always provide genuinely useful answers. Never sacrifice accuracy for a joke. Sarcasm is playful, never cruel; avoid humiliation, personal attacks and punching down.

**Serious-topic override, stronger than every style fragment:** Use a caring, professional tone for sensitive employee matters, medical issues, customer complaints, financial hardship, emergencies and other serious situations. Suspend sarcasm and roasting. Do not rely solely on a keyword detector; include this instruction in every shared prompt and verify representative scenarios.

**Common behavior:** Be transparent that this is AI. Ground business claims in permitted current records and citations. Admit missing facts. Avoid repetitive acknowledgments and unnecessary questions. Honor response-length preferences and needed detail. Personality changes expression only: backend permissions, available tools, required confirmation, financial disclosures, facts, pricing calculations and action outcomes stay identical.

## 3. Persistence, API and settings workflow

Recommended implementation contracts below are proposed additions, not existing APIs:

1. Add a typed `assistant_preferences` subdocument to the canonical User record. Store `personality_key` separately from `voice`; also support the attached scope's display name, response length and spoken-replies preference through this same boundary. Never infer voice from personality or overwrite one when saving the other.
2. Read and update the authenticated user's record with both `tenant_id` and user `id` filters. Derive both from server authentication. Reject arbitrary user/tenant targets and unknown keys; allowlist fields so a settings update cannot modify roles, permissions, credits or confirmations. No client-supplied prompt fragments.
3. Resolve personality as explicit user choice → optional validated shop default → `ops_partner`. Start with per-user choice and the system default; a shop-default editor is optional, not a V1 dependency. If added, store it on the canonical Tenant, require existing shop-settings write permission and never override an explicit user choice. Missing fields need no bulk migration; unknown stored keys fall back safely. Invalid update requests fail visibly without changing the saved selection.
4. Add GET/PUT `/api/assistant/preferences` to the existing router/service and access checks. GET returns saved and effective preferences, the personality source (`user`, `shop` or `system`) and the five display options. PUT validates and returns confirmed saved/effective values. Adapt the donor endpoint behavior; do not add a legacy route alias without an actual consumer.
5. Add Assistant Settings in MVP's existing settings shell, reachable from both assistant interfaces. Proposed route `/settings/assistant`; use the current route/navigation conventions and assistant access checks. Personal preferences should not require shop-administrator access. Shop-default editing, if implemented, is a separate permission boundary.
6. Show five keyboard-accessible selectable cards with selected state, full description, saving/error feedback and a clearly visible fifth-card warning. Use radio-group semantics and a label that says personality/tone. Keep Voice, Preview, display name, response length and spoken replies as independent controls. Settings persistence must not require a paid model call.
7. Reuse one authenticated frontend preference/conversation state owner across full page and floating dock. Clear user-specific caches at logout and tenant/user change. Refetch after login. On failed save retain or restore the last confirmed selection; handle rapid changes without stale responses replacing newer saved values.
8. Changing personality preserves conversation IDs, messages, summaries, approved memory, citations and proposals. Resolve current saved personality on each new text turn; apply it to resumed conversations rather than replaying an old style as instructions. Old messages remain historical evidence. Personality is a structured preference, not a second free-form memory entry.
9. A successful save affects the next assistant response on every surface. For an active Realtime session, use a validated server-controlled update only if the current API supports the required control; otherwise reconnect before the next spoken turn, keeping the same canonical conversation. Show that transition honestly. Voice changes may require a separate reconnect based on API limitations; neither operation deletes history or changes the other preference.

## 4. One prompt composition path, with output boundaries

Proposed module: `backend/app/services/assistant_personality.py`, called by the existing assistant service and Gateway adapter. It owns the catalog, validated resolution and instruction composition; it is not a conversation service. The frontend API helper remains `frontend/src/lib/businessAssistant.js`.

The backend composes common identity, truthfulness, sensitive-topic and action-safety rules; the selected personality fragment; permitted user preferences; bounded conversation summary/history; and validated current tool/context data. Retrieved notes, documents and memory remain untrusted data. They cannot select another personality, rewrite instructions or grant tool access. Use the existing Gateway prompt/version records for traceability; do not create competing prompt registries. Record personality key/version in existing message/session metadata without logging secrets or private prompts.

Text through the AI Gateway and Realtime session creation/update both call this same builder. Transport adapters may format the resulting instructions for their API, but must not define personalities independently. Any approved speech-to-text → canonical chat → speech fallback uses the same resolution path. Preview speech uses the separately selected supported voice; a canned preview does not demonstrate conversational personality application.

Assistant narration and customer-facing artifacts have explicit output purposes. Email, invoice, document and other customer-communication generation defaults to a neutral professional business-writing policy and excludes the selected personality fragment, including when sarcastic commentary accompanies a draft. Generate the artifact through that neutral boundary; do not copy a sarcastic chat answer into a customer draft. Personality must not alter structured action payloads or financial document text. An explicit request to change a particular draft's tone still follows normal preview/edit/confirmation and sending permissions; personal settings never imply such a request. No automatic sending.
