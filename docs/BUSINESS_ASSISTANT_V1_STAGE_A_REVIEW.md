## 3. Missing functionality and specific launch risks

The following are source findings, not reproduced runtime incidents:

1. **Real text generation and multi-turn orchestration — CONFIRMED gap.** `ask_assistant` meters a simulated request then calls keyword handlers. It does not compose stored history, approved memory and tool results into a provider conversation. The Gateway has no real external call in its inspected request path. Card selection cannot fix this.
2. **Financial answer correctness — CONFIRMED gap.** The “overdue invoice” branch filters non-paid records without testing due dates, sorts by creation descending, caps at 25 and sums stored balances. `models/invoice.py:61` has `due_date`; canonical invoice list/detail derive balances using payment sums (`routers/invoices.py:82–99,146`). Launch must reuse that financial basis and apply real due dates, paid/void/refund rules, shop-local dates and explicit pagination. “Oldest” must refer to the cited result set. Do not expose a sampled subtotal as total receivables or invent missing due dates. Pricing/financial formula ownership stays outside AI.
3. **Real operational records — CONFIRMED partial behavior.** Production “blocker” output currently counts recent Work Orders and discloses missing stage dates. A task count is not proof of a production delay. Quote follow-up lists lack last-contact evidence. Customer context snapshots contain only label/name/status, not complete order history. Schedule and staffing tools need precise permitted read models and local-date handling.
4. **User privacy inside a shop — CONFIRMED inconsistent filters; impact needs tests.** Lists use `tenant_id + user_id`, but `_conversation`, `delete_memory`, proposal and voice-session ID lookups are tenant-only. Some follow-up updates use only IDs. Adopt user-private conversations/preferences/memory by default and authorized linked-record access for tools; add same-tenant other-user and cross-tenant tests to every affected read/write. No new parallel records.
5. **Action exactly-once protection — LIKELY race.** `execute_proposal` reads confirmed status, checks any execution key, sets executing without a conditional state claim, then calls canonical services before inserting execution evidence. The router permits a missing idempotency header. Concurrent or interrupted executions could duplicate an effect or leave a proposal stuck; this assessment did not trigger the race. Require a stable key, atomic claim and canonical deduplication/recovery, including success-before-recording-failure. Recheck content/targets on confirm and execution.
6. **Voice parity, lifecycle and cost trust — CONFIRMED gaps.** Realtime instructions are a separate fixed string, expose only `propose_assistant_action`, and do not seed canonical history/read-tool context. `AssistantPanel.jsx:273–299` keeps transcripts locally, converts audio tokens to seconds by dividing by 50, accepts client forwarding and suppresses metering errors. Backend `record_voice_usage:1333` accepts those numbers, overwrites duration fields and calls simulated metering. Session creation checks positive credits and start frequency, not a session budget reservation/duration cap. It is not verified provider accounting or enforceable ongoing spend control.
7. **Budget race and simulated “actual” cost — CONFIRMED sequencing; concurrent overspend LIKELY.** Governance reads daily usage before action creation/reservation and does not reserve in-flight provider spend. Persisted cost is based on estimate, not provider usage. Add atomic admission/reservations, duration/output/tool-round limits, observed usage reconciliation and incomplete/unknown cost states. Failed or interrupted requests may still incur provider costs; separate actual provider liability from customer credit policy.
8. **Donor transplant risk — CONFIRMED incompatible assumptions.** Original code includes founder access shortcuts, legacy `jobs`/dollar math, broad context, tenant-wide rolling personal memory, direct provider wrappers and client-history merging. Reuse ideas through MVP's permissions, cents, canonical records and Gateway. No wholesale import or destruction of historical records.

## 5. Recommended architecture and employee workflow

One assistant service owns authenticated conversation orchestration. Text and voice are transport adapters around the same context resolver, allowlisted read tools, proposal creation and canonical action executor. Keep the existing Gateway as the only provider admission, capability, usage, credit and cost authority; extend its lifecycle rather than constructing another engine or wallet.

For text, use a backend OpenAI Responses adapter with typed function tools; validate tool arguments and perform reads/proposals on the application side. This fits the documented [OpenAI function-calling flow](https://developers.openai.com/api/docs/guides/function-calling). It does not grant a model database credentials, arbitrary queries, SQL/Mongo writes or action approval authority.

For voice, keep MVP's Realtime WebRTC primary transport and add backend observation/control of the same session. A server connection can monitor events, update instructions and respond to tools while the browser carries audio, as described in [OpenAI server-side controls](https://developers.openai.com/api/docs/guides/voice-server-controls?api=realtime&voice-api=realtime). This is the recommended means to share tools, persist transcripts and enforce session limits; verify exact API/model compatibility at Stage D. Do not automatically migrate to another voice product or assume existing model defaults are valid. If needed, one recorded STT → this same assistant → TTS fallback uses the same permissions, memory and costs. Text remains usable when voice is unavailable.

The employee opens the current page or dock, asks an ordinary-language question and gets a concise response linked to relevant permitted records. Follow-ups use bounded canonical context, with current data rechecked when the question depends on changing facts. Ambiguous people/orders/dates are clarified. Unavailable data is stated plainly. “Create a task/note” or “prepare an email” produces a preview with editable payload and explicit confirmation; success is shown only after the existing canonical service returns and the result is verified. No automatic customer sending or financial mutations.

The full page and dock share the active conversation. Assistant Settings offers all five personalities, independent supported voice/preview and remembered user preferences. Personality changes preserve history and memory. The original four plus Sarcastic & Funny use the [integrated plan's exact rules](BUSINESS_ASSISTANT_V1_IMPLEMENTATION_PLAN.md#2-five-personality-cards-and-shared-definition); serious-topic care and professional customer artifacts override style. MVP mode/personality never expands permissions. Settings cards must be usable and accessible at launch; visual polish cannot delay core chat/data/action work.

Suggested additive ownership: existing assistant router/models and service; narrow `assistant_context`/`assistant_tools`/`assistant_personality` helpers only where they simplify the current service; an OpenAI adapter within the Gateway responsibility; one shared frontend assistant state owner and a settings component. Module names are proposals, not newly implemented services. One primary implementer; no subagents or other chats were dispatched. Route/Gateway changes need a short integration note for separately owned work; onboarding/help source files, pricing engine and Webstore payment code remain out of scope.

## 7. Cost controls and safeguards against unnecessary requests

- Admit provider work through existing Gateway permissions, entitlements, capability status, credits and tenant budget checks. Reserve concurrent spend before dispatch. A positive balance check alone is not enough for a long voice session.
- Track tenant, user, feature/capability, provider/model, request/session/tool identifiers, real input/output usage, latency, outcome and provider event ID. Retain existing separate credit and provider-cost ledgers. Distinguish estimates, observed usage and reconciled cost; unknown is not zero. Never present local simulations or token/50 duration guesses as provider evidence.
- Use one conversational model/tool loop with bounded context, output and tool rounds. Ordinary lookup may require a tool-result completion; do not promise every turn takes exactly one paid call. Avoid redundant classify → parse → chat → rewrite chains when one tool-capable conversation suffices. Deduplicate retries/in-flight requests and stop abandoned work where possible.
- Navigation, settings saves, history reads, known calculations, direct record rendering and deterministic supported quick actions need no model call. Reuse fresh permitted read results briefly with explicit freshness and tenant/user scope; recheck on changes. No timer-driven polling that sends prompts, background summaries on every message or automated personality/voice previews.
- Bound voice session duration, idle time, reconnects, simultaneous sessions and output; reserve/update budget and end sessions server-side. Browser events are UI signals, not a trusted spend ledger. Handle missing final usage as incomplete and reconcile it; do not swallow metering errors while continuing unlimited service.
- User-approved durable memory is saved deterministically. Summarize only when a bounded history threshold requires it, through the same metered capability. Include cancelled/failed calls with observed provider usage; do not assume all failures are cost-free or bill a user repeatedly for an execution retry.
- All automated tests mock paid providers. After safety checks, present a small live test scope and request a spending cap before the first paid evaluation. No live spend was authorized or incurred in Stage A. H7's final production/commercial values are not waived by the release requirement.
